## 1. The finding, first

**The mesh cannot tell the difference between a turn that did nothing and a turn that did
everything. Both are logged as `turn.discarded … nothing was sent, published, or requested`.**

```
mission spend                              1,604,221 tokens   (31 min, 21 turns)
in turns logged reason=no_ops (8 turns)      701,592 tokens   (43.7%)
  genuinely destroyed  (repo parser bug)      47,825   6.8%   pm                    §2.1

  nothing lost, only mislabelled              540,129  77.0%  qa, frontend x3, tech-lead  §2.4
```

**That split is the finding, and it is why `no_ops` is unusable as a waste metric.** The same event
and the same summary string cover a turn whose well-formed mission brief was destroyed by a regex,
and a turn that published three artifacts, transitioned them, claimed a task and sent four messages,
all durable. A first pass over this log reads "69% of spend bought nothing", which is wrong: **66% of
the discarded volume is work that landed perfectly.** (The 1,191,376-token / 28% loss cited in
`tests/core/turn-discarded.test.ts:16-20` is worth re-checking for the same conflation.)

The cause is that a turn has **two output channels** — the MCP tool channel and the `mesh-json` ops
block — and they fail and are measured independently:

- the ops block is parsed **all-or-nothing**, so one malformed byte anywhere destroys every op in
  the array, at full price, with no salvage and no retry;
- work done through MCP in the same turn is **already committed**, so a "discarded" turn leaves the
  mesh half-applied;
- the watchdog's work-detection reads **only** the ops block, so the three most productive turns of
  the run were each recorded as *"no work was produced"* and flagged for driver rotation.

One of the three losses is a straightforward parser bug in this repo, and the lost content is
provably recoverable (§2.1). The mission's central artifact is now deadlocked in `DRAFT` carrying
two recorded approvals that had no effect (§5).

The agents themselves performed well. tech-lead approved with sha256 citations and then *detected*
the DRAFT deadlock and asked the right seat to fix it; pm returned a per-invariant conformance
verdict and corrected the architect's stale reference. None of the problems below are
writing-quality problems.

### 5.2 The real mechanism is broader than versioning: approving a DRAFT artifact is a silent no-op

My first reading of this section named the trigger as *"version an artifact that is already
APPROVED."* That is one route in, not the rule. At 20:24:31 it happened to an artifact that had never
been versioned and had never been approved:

```
20:24:31  review.approved      actor=tech-lead   art-M37WMP320082a4591143  (pm's RequirementsDoc)
20:24:31  artifact.transition  actor=system      -> DRAFT   derived, gateSatisfied: true
```

That artifact had **no prior transition event of any kind** — it sat in its initial `DRAFT` state
because pm published it, tried to self-approve, was denied, and nobody else was asked (§19.1). tech-lead
finally reviewed it and approved it, and the approval derived `DRAFT`.

So the general rule is: **an `approve` on an artifact that is not in a reviewable state emits the
approval, derives the artifact's existing state, reports `gateSatisfied: true`, and refuses nothing.**
Three instances now, on three artifacts, from two different seats:

```
19:45:19  pm        -> ArchitectureDocument v2  (DRAFT because it had just been versioned)
19:46:32  tech-lead -> ArchitectureDocument v2  (same)
20:24:31  tech-lead -> RequirementsDoc v1       (DRAFT because it was never submitted)
```

Versioning is simply the commonest way an artifact ends up back in `DRAFT` while approvals are in

**So the authority model is enforced correctly where it matters.** The state machine does not count a

`review.reviewer-cannot-settle` says on the request side (§9.1). There is no authority hole.

**What is wrong is the reporting.** Six times the log records:

action, not the effect.** It is the run's most repeated shape, and the cheap fix is the same everywhere —
refuse, or at minimum tell the actor, when an op has no effect.

### 9.2 The worst instance: a reviewer rejected a patch 35 minutes after it shipped, and the rejection was a no-op

Full life of frontend's UI CodePatch (`art-M37X7NEQ002f146676b5`):

```
19:52:41  frontend   publishes it
20:04:55  tech-lead  review.approved        -> APPROVED -> VERIFIED
20:05:26  tech-lead                         -> MERGEABLE
20:08:20  architect                         -> MERGED       (lands in git as be7e65f)
20:42:23  tech-lead  REJECT sent as a MESSAGE — no verdict recorded (§21.2)
20:43:11  tech-lead  review.rejected        -> MERGED -> MERGED     no-op
```

tech-lead approved this patch, it merged into `main`, and **35 minutes later tech-lead formally rejected
the same artifact** — first as a message that recorded nothing, then, after the runtime's remediation
message, as a correct `reject` op. That op emitted `review.rejected` with a substantive comment and
changed nothing, because there is no `MERGED -> REJECTED` edge.

Refusing to un-merge on a reject is the right design. **Reporting it as a recorded rejection is not.** The
event log now contains a `review.rejected` verdict, from the seat that owns code review, against a patch
that is in `main` — and nothing anywhere says the verdict was inert. An auditor reading this log sees a
rejected patch shipped. The reviewer, for its part, has no signal that its rejection did not take, and
`artifact.transition … to: MERGED` alongside it reads as confirmation.

The correct behaviour is a refusal with a route: *"this artifact is already MERGED — open a revert or a new
revision."* Note the runtime already does exactly that kind of thing well elsewhere (§21.2's
`verdict.message-only` text is a model of it), so the machinery for saying so exists.

This is the single most consequential instance of the family in triage item #8: six no-op approvals, two
approvals on `DRAFT`, `patch.merged` on a failed merge, empty replies closing real asks — and now a
rejection of shipped code that reads as authoritative and did nothing.

**What the data does support** is the number itself: **only about 30% of message deliveries cause a wake.**

`marketing` is the limiting case: zero messages ever addressed to it, `goal.progress` emitted zero times,

**Mechanism, now traced — and it is not `drainGathered`.** `gather()` has exactly one call site, inside
the `message.sent` branch (`scheduler/src/index.ts:474-477`), so the coalesced-wake path never touches
interest events at all. The hypothesis recorded here earlier was wrong. The real causes are two gates in
`requestActivation`:

- **`:610-617` — the silent drop.** When the agent is busy, only `message`, `recovery` and `explicit`
  reasons are stashed in `wakeAfterTurn`. An `interest_event` matches none of them, so nothing is
  stashed — and the function still **returns `true`**, which `supervisor.ts:2527` reads as
  `{ queued: true }`. The wake is gone and every caller was told it landed.
- **`:618-625` — relabelling.** An already-queued entry is merged and its `reason` discarded unless the
  new priority is higher. Interest wakes are SKIM=3 (`triageRules: []` ⇒ `:553`); message priorities run
  2/4/6/9. So an interest wake arriving against a queued NORMAL-or-above message is absorbed and the
  turn is logged as `kind: "message"`.

That second gate means **the 39-vs-4 census above overstates the suppression**: some of those 39
message-wakes are interest wakes wearing a message label. The *cause* stands — interests are not
independently scheduling seats — but the ratio is not a clean measurement of it, and neither is the
`INFORM`-triggered-29-wakes figure in §22.1, which is why that retraction was itself unreliable.

`max_active_agents` never refuses an activation; it lengthens the running and queued windows, which is
what holds both gates open. It is the multiplier, not the cause.
